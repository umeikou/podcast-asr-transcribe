# 中文播客转写的质检与校正方法

原始 ASR 输出直接看会很难受：口语赘余、专名误识、中英混排混乱。以下是经过实测的有效处理法。

## 一、先体检，再出稿

**永远先跑 `--probe`**，不要直接渲染。

```bash
python3 render_transcript.py result.json --probe
```

输出三块信息，分别对应三类问题：

1. **说话人分布** —— 每人的段数/时长/占比。若某人占比 <3% 且段数零星，多半是聚类噪声或背景笑声被误判。
2. **英文词频表** —— **这是发现专名误识别最有效的手段**。真名会高频出现且拼写正常；误识往往拼写可疑、频次低。逐条扫一遍低频项。
3. **单字母拆散告警** —— `A I`、`V B A`、`M C P`、`G D G` 这类被空格拆开的缩写，渲染时会自动合并。

## 二、专名校正：只改高置信度的

### 判据（必须满足其一才改）

- **语义可推理**：`科脑` 出现在 "Linux 科脑" 语境 → 必是 `内核`（kernel）
- **同源可推**：`Omab` 是 DHH 的 Ubuntu 项目 → 实为 `Omakub`（Omarchy 的前身）
- **口播线索**：说到"小龙虾" → `OpenCLow` 实为 `OpenClaw`（吉祥物）
- **数字/字母形近**：`三十七三针纳斯` → `37signals`

### 绝不硬猜

以下情形保留原文，在文档里标 `[存疑]` 交给用户：

- 疑似产品名但无法确认（`OmaC`、`Worso`、`M Chat`、`Person A`）
- 人名/机构名无法验证
- 数字、金额、版本号听不真切

**硬猜的代价远大于留疑**——用户信任建立在"不改错"上，不是"改得多"。

### 常见误识模式（中文技术播客）

| 类型 | 例子 | 处理 |
|---|---|---|
| 缩写被空格拆散 | `A I`→AI，`M C P`→MCP，`V B A`→VBA | 脚本自动合并 |
| 字母串变无意义词 | `A G N A` → 实为 `Agent` | **需显式校正**，自动合并只会得到 `AGNA` |
| 英文品牌音译 | `三十七三针纳斯` → 37signals | 显式校正 |
| 技术词谐音 | `科脑` → 内核 | 显式校正 |
| 形近项目名 | `Omachi`/`Omab` → Omarchy/Omakub | 显式校正 |
| 中英混读丢词 | `OpenCL` → `OpenClaw` | 显式校正 |

### 校正表写法

`render_transcript.py` **跑两遍校正**：先处理原始形态（含空格），再处理合并后形态。所以 `"A G N A"` 和 `"AGNA"` 两种写法都能命中，建议都写上。

长串会自动排前面，避免短串先命中把句子改残。例：先替换 `"三十七三针纳斯的这个创始人"`，而不是先替换 `"三十七"`。

## 三、机洗规则（可全自动，不需判断）

脚本 `clean()` 已内置，无需干预：

- 中文与中文之间的多余空格 → 删除（`我 们` → `我们`）
- 中文后的半角标点 → 全角（`，。？！；：`）
- 连续空格压缩
- 单字母序列合并（2–6 个）

**不动**的部分（保持原貌）：
- 口语赘余（"啊"、"对"、"嗯"）—— 这是播客真实语感，删了反而不自然
- 断句与分行 —— 按 ASR 的段落切分，不重排
- 无法确认的专名

## 四、说话人姓名映射

### 可以确认的依据

1. **自我介绍**："我是 xxx"
2. **他人称呼**：被叫"小白"、"某高老师"
3. **职能自述**："我们写的语音转文字服务" → 该产品的负责人
4. **节目 shownotes**：主播名单 + 分工（"本期主播：A、B、C"）

### 无法确认时怎么办

**明确标注不确定，不要分配姓名。**

```
| SPEAKER_1 | 某高老师 / 高春辉 之一 | 28.1% | 未出现自称，对话中以"老高"第三人称指代他人 |
```

并在表下注明："说话人为声纹聚类结果，标签顺序不代表出场顺序。SPEAKER_1 与 SPEAKER_2 的身份无法从音频内容唯一确认。"

**注意陷阱**：对话里出现"老高说……"这类第三人称，恰恰说明**说话人不是老高**。别把被提到的人名安到说话人头上。

## 五、热词与 initial_prompt 策略

### hotwords

- 来源：shownotes 的专名 + 节目名 + 主播名 + 领域术语
- 数量：20–40 个，太多反而稀释权重
- 实测效果：`Omarchy` 全片 22 次正确、3 次误拼；未加时误拼率更高

### initial_prompt

写一句**场景 + 语种 + 期望行为**的说明，例如：

> 这是一档中文科技播客，主持人与嘉宾围绕操作系统、开源生态、AI Agent 与软件商业模式展开讨论。对话中会频繁夹杂英文技术名词，如 Omarchy、Arch Linux、Hyprland、DHH、Ruby on Rails、MCP 等，请准确保留中英混读的原始表达。

不要写"请准确转写"这种空话，要具体到领域和专名。

## 六、产出格式

| 文件 | 用途 |
|---|---|
| `<标题>.md` | 主交付：元信息 + 说话人对照表 + 带时间戳正文 |
| `<标题>.txt` | 纯正文，喂给摘要/检索/二次加工 |
| `<标题>.srt` | 字幕，含 `[说话人]` 标记 |
| `result_<id>.json` | 原始结果，保留可复现 |

**合并同说话人的连续段落**：852 段 → 279 段，可读性提升明显，但 `srt` 仍按原始段落输出（字幕需要细粒度）。

## 七、成本参考

1.6 小时音频，标准档 + 分离：**1.28 元**（96 计费分钟 × 0.8 元/小时）。同档位优化档约 0.75 元，但会丢词级时间戳且专名变差。对播客转写，标准档性价比更高。
